# Feature: Client Share Links

A secure, expiring link plus a 6-digit PIN that lets a client view selected credentials and env variables of their own project, without needing an account.

**For AI tools (Antigravity):** read this file together with `PRD.md`, `ARCHITECTURE.md`, `DESIGN.md`, `RULES.md`, `DECISIONS.md`, `SECURITY.md`, `TEST_PLAN.md`, `TASKS.md` and `MEMORY.md` before writing any code. Work one task at a time (see the Tasks section). If anything here conflicts with `RULES.md` or `SECURITY.md`, stop and ask.

---

## 1. Goal

Today a team member must send client credentials over chat or email. This feature replaces that with a controlled share:

1. A team member selects which credentials and env variables the client may see.
2. They choose how long the link stays valid.
3. The system creates a **link** and a **6-digit PIN**.
4. The team member sends the link and the PIN to the client (ideally through different channels).
5. The client opens the link, enters the PIN and sees only the selected items.
6. The team member can revoke or extend the link at any time and sees who accessed it.

---

## 2. Scope

### In scope
- Create, list, view, revoke, extend and delete share links per project
- Choose exactly which credentials and env variables each link exposes
- Expiry presets: 30 days, 60 days, 120 days, 1 year, no expiry
- 6-digit PIN generated by the system, shown once to the creator
- Public client page: PIN gate, then a read-only view of the shared items
- Reveal and copy for each secret on the client page
- PIN attempt limits and lockout
- Audit logging for both team actions and client access
- Optional maximum number of views
- Regenerate PIN

### Out of scope (for this feature)
- Client accounts or logins
- Clients editing anything (read-only only)
- Sending the link or PIN by email or SMS automatically (manual copy only for now)
- File attachments
- Sharing across multiple projects in one link
- Client-side notifications

### Why ADR-023 is needed
The client has no Supabase account, so there is no user session for RLS. Public share requests must read data through a tightly scoped server module using the service-role client. This is the one allowed exception to "service-role never reads secrets", and it is only safe because:

- The module only reads items listed in `share_link_items` for one validated, unexpired, unrevoked share.
- The module is `server-only` and is the only code allowed to do this.
- Every read is audit logged.

## 5. User Flows

### 5.1 Team member creates a link
1. Open a project, go to the **Share** tab.
2. Click **Create share link**.
3. Fill in: label (for example "Acme Corp, handover"), expiry preset, optional max views.
4. Select items: tick credentials and env variables to include.
5. Click **Create**.
6. A dialog shows the **link** and the **6-digit PIN** with copy buttons and a warning: *"The PIN is shown only once. Send the link and PIN through different channels."*
7. The link appears in the list.

### 5.2 Client opens the link
1. Client opens `https://vault.company.com/share/<token>`.
2. A PIN screen appears with the project name only.
3. Client enters the 6-digit PIN.
4. On success, the client sees the shared items, grouped as Credentials and Env Variables (by environment).
5. Secrets are masked. The client clicks Reveal or Copy for each.
6. The session ends after inactivity, and the client must enter the PIN again.

### 5.3 Team member manages links
- See status per link: Active, Expired, Revoked, Locked.
- Revoke immediately.
- Extend expiry (choose a new preset or date).
- Regenerate the PIN (old PIN stops working, new PIN shown once).
- Change which items are shared.
- View access history.

## 6. Functional Requirements

### 6.1 Link creation
- FR-01: Each link belongs to exactly one project.
- FR-02: The link token is generated server-side with `crypto.randomBytes(32)`, encoded as base64url (43 characters). It is never derived from IDs or timestamps.
- FR-03: Only a **hash** (SHA-256) of the token is stored. The full link is shown once at creation, together with the PIN. Because the token is high entropy, a plain SHA-256 hash is sufficient.
- FR-04: The PIN is a random 6-digit number from `crypto.randomInt(0, 1_000_000)`, left-padded with zeros.
- FR-05: The PIN is never stored in plain text. Store a salted `scrypt` hash with a server-side pepper (section 8).
- FR-06: At least one item must be selected.
- FR-07: A label is required (max 80 characters).

### 6.2 Expiry
| Preset | Behavior |
|---|---|
| 30 days | `expires_at = now + 30 days` |
| 60 days | `expires_at = now + 60 days` |
| 120 days | `expires_at = now + 120 days` |
| 1 year | `expires_at = now + 365 days` |
| No expiry | `expires_at = null`, `never_expires = true` |

- FR-08: Expiry is evaluated **server-side on every request** (PIN check and every reveal), never only at link open.
- FR-09: Selecting **No expiry** shows a clear warning and requires confirmation: *"Anyone with this link and PIN can view these secrets until you revoke the link."*
- FR-10: The list shows remaining time ("Expires in 12 days") and highlights links expiring within 7 days.
- FR-11: Extending recalculates `expires_at` from now (or from the current expiry, decide in review).
- FR-12: Expired links show the same generic message as invalid links.
- FR-13 (optional): custom date picker with a maximum of 1 year.

### 6.3 Item selection
- FR-14: Selectable items are the credentials and env variables of the same project.
- FR-15: Selection is stored in `share_link_items` (item type plus item ID).
- FR-16: Items are shown **live**. If the team edits a shared password, the client sees the new value. If an item is deleted, it disappears from the share.
- FR-17: Env variables can be selected one by one, or by whole environment (Dev, Staging, Production). Selecting a whole environment adds the current variables only. New variables added later are not included automatically.
- FR-18: Production items show a red Production badge and an extra confirmation when selected.
- FR-19: Credential **notes are never shared**. The client sees service name, login URL, username and password only. Env variables show key and value only.
- FR-20: Team members can edit the selection after creation.

### 6.4 Client page
- FR-21: Shows the project name and company name only. No other projects, clients, team member names or internal notes.
- FR-22: Read-only. No edit, delete or add actions.
- FR-23: Secrets are masked by default. Reveal and copy use the same behavior as the internal `SecretField`: auto-hide after 15 seconds and clipboard cleared after 30 seconds.
- FR-24: A "Copy all as .env" button is **not** included in the first version (see Open Questions).
- FR-25: A visible notice: *"This page is confidential. Do not share the link or PIN."*
- FR-26: Session ends after 20 minutes of inactivity. The client must re-enter the PIN.

### 6.5 Limits and controls
- FR-27: Optional **max views**. A "view" is one successful PIN entry. When the limit is reached, the link stops working.
- FR-28: Manual revoke is immediate. It takes effect on the next request and ends active client sessions.
- FR-29: Regenerating the PIN invalidates the old PIN and any active client sessions.
- FR-30: Deleting a link removes it and its item list, but its audit log entries stay.

## 7. Data Model

Create these in a migration (for example `supabase/migrations/<timestamp>_share_links.sql`). All tables have RLS enabled.

```sql
create table share_links (
  id uuid primary key default gen_random_uuid(),
  project_id uuid not null references projects(id) on delete cascade,
  created_by uuid not null references profiles(id),
  label text not null check (char_length(label) between 1 and 80),

  token_hash text not null unique,        -- SHA-256 of the token, hex
  pin_hash text not null,                 -- scrypt hash (with pepper)
  pin_salt text not null,                 -- random per link

  expires_at timestamptz,                 -- null when never_expires
  never_expires boolean not null default false,
  max_views integer check (max_views is null or max_views > 0),
  view_count integer not null default 0,

  status text not null default 'active'
    check (status in ('active', 'revoked')),
  revoked_at timestamptz,
  revoked_by uuid references profiles(id),

  failed_attempts integer not null default 0,
  locked_until timestamptz,
  session_version integer not null default 1, -- bump to end all client sessions

  last_accessed_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

  check ((never_expires = true and expires_at is null)
      or (never_expires = false and expires_at is not null))
);

create table share_link_items (
  id uuid primary key default gen_random_uuid(),
  share_link_id uuid not null references share_links(id) on delete cascade,
  item_type text not null check (item_type in ('credential', 'env_variable')),
  item_id uuid not null,
  created_at timestamptz not null default now(),
  unique (share_link_id, item_type, item_id)
);

create table share_link_attempts (
  id uuid primary key default gen_random_uuid(),
  share_link_id uuid not null references share_links(id) on delete cascade,
  ip_address inet,
  success boolean not null,
  created_at timestamptz not null default now()
);

create index on share_links (project_id);
create index on share_link_items (share_link_id);
create index on share_link_attempts (share_link_id, created_at);
create index on share_link_attempts (ip_address, created_at);
```

### RLS rules
- `share_links` and `share_link_items`: Admin and Manager with access to the project can select, insert, update and delete. Developers have no access. **No anonymous access.**
- `share_link_attempts`: insert from the server only, select for Admin only. No update or delete.
- `pin_hash`, `pin_salt` and `token_hash` must never be returned to the browser. Use a view or select only safe columns in the service.
- Public client access never uses RLS. It goes through `share-access.service.ts` (section 9).
- Extend `audit_logs` actions with the values in section 12. The table stays append-only.
- Write RLS tests (see `TEST_PLAN.md` style): a Developer cannot read share links, and anon cannot read any share table.

## 8. Security Design

A 6-digit PIN has only 1,000,000 possibilities, so it is **weak on its own**. Security comes from combining it with the long random token and strict limits. Do not weaken any of these.

### 8.1 Two factors, two channels
- The link carries a 256-bit random token (cannot be guessed).
- The PIN is a second factor. The UI reminds the creator to send them through **different channels** (link by email, PIN by phone or chat).

### 8.2 PIN protection
- Hash with `crypto.scrypt` (built in, no new dependency) using a per-link random salt plus a server-side pepper `SHARE_PIN_PEPPER`.
- Compare with `crypto.timingSafeEqual`.
- **Pepper matters:** without it, a leaked database would let an attacker brute-force all 1,000,000 PINs offline in seconds. With the pepper stored only in the host environment, a database leak alone is not enough.
- Never log or return the PIN after creation. If the creator loses it, they regenerate.

### 8.3 Brute-force protection
- Maximum **5 failed PIN attempts per link**. After the 5th, set `locked_until = now + 30 minutes`. After repeated lockouts (3 in 24 hours), set the status to a locked state requiring manual unlock by an Admin or Manager.
- Additionally limit attempts **per IP**: maximum 10 failed attempts per hour across all links.
- Add a small constant delay (about 500 ms) on every failed attempt.
- All checks run server-side. Record every attempt in `share_link_attempts`.
- Lockout and attempts are tracked per link, so an attacker cannot reset them by clearing cookies.
- Show the generic "Incorrect PIN" message. After lockout show "Too many attempts. Try again later or contact your project contact."

### 8.4 No information leaks
- An invalid, expired, revoked or unknown token returns the **same** generic page: *"This link is invalid or has expired."* Do not reveal which case it is.
- Use constant-time comparisons for token hash lookups where practical.
- The PIN screen shows only the project name, never item counts or contents.

### 8.5 Client session
- After a correct PIN, issue a signed session cookie: HMAC-SHA256 using `SHARE_SESSION_SECRET`, containing `share_link_id`, `session_version` and `exp` (20 minutes, sliding refresh on activity).
- Cookie flags: `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/share`.
- On **every** server action (list, reveal), re-validate: signature, cookie expiry, link status, `expires_at`, `max_views`, `session_version`, and that the requested item belongs to this share. Never trust the cookie alone.
- Revoke, PIN regeneration and expiry take effect immediately because of these re-checks.

### 8.6 Secrets handling
- Items are decrypted only on an explicit Reveal or Copy action, through a server action, using `lib/crypto.ts`.
- Never include secret values in the page's initial HTML, props or list responses.
- The list response contains only: item ID, type, service name or key, login URL, username, environment.
- Responses containing secrets use `Cache-Control: no-store`.
- **IDOR check:** a reveal request must verify that `item_id` exists in `share_link_items` for **this** share. Knowing another item's ID must not work.
- Every reveal writes an audit log entry **before** the value is returned. If logging fails, nothing is returned.

### 8.7 Page and transport protections
- HTTPS only.
- Headers on `/share/*`: `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex, nofollow`, `Cache-Control: no-store`, `X-Frame-Options: DENY`, strict CSP.
- Add `<meta name="robots" content="noindex, nofollow">`.
- The token appears in the URL, so do not send it to analytics, error trackers or logs. Redact `/share/<token>` in any logging.
- Do not load third-party scripts or fonts on the share pages.

### 8.8 Rate limits on creation
- Limit link creation per user (for example 20 per hour) to prevent abuse.

### 8.9 Environment variables to add

| Variable | Exposure |
|---|---|
| `SHARE_PIN_PEPPER` | Server only. 32 random bytes in hex. |
| `SHARE_SESSION_SECRET` | Server only. 32 random bytes in hex. |

Add placeholders to `.env.example` and the validated `lib/env.ts`. Keep a secure backup of the pepper. If it is lost, all existing PINs stop working and must be regenerated.

- Dashboard actions use `getCurrentUser()` and `requireRole()`, and the user's session client (RLS applies).
- Public actions never read cookies for Supabase auth. They verify the share session only.
- UI components contain no database logic.
- Reuse the existing `SecretField`, `DataTable`, `ConfirmDialog`, `EmptyState` and `ErrorState`. Do not duplicate them.

## 10. Server Actions and Services

### Team actions (`share-link.actions.ts`, authenticated)

| Action | Input | Result |
|---|---|---|
| `createShareLink` | projectId, label, expiryPreset, maxViews?, items[] | `{ url, pin, shareId }` (shown once) |
| `listShareLinks` | projectId | safe fields only (no hashes) |
| `updateShareItems` | shareId, items[] | updated list |
| `extendShareLink` | shareId, expiryPreset | new expiry |
| `regeneratePin` | shareId | `{ pin }` (shown once), bumps `session_version` |
| `revokeShareLink` | shareId | revoked, bumps `session_version` |
| `unlockShareLink` | shareId | clears lockout |
| `deleteShareLink` | shareId | deleted |
| `getShareAccessHistory` | shareId | attempts and access log |

Each action: verify session and role, verify project access, validate with Zod, call service, write audit log.

### Public actions (`share-access.actions.ts`, share session)

| Action | Input | Result |
|---|---|---|
| `verifyPin` | token, pin | sets share session cookie, or generic error |
| `getSharedItems` | (cookie) | list of safe fields, no secrets |
| `revealSharedItem` | itemType, itemId | decrypted value (no-store), audit logged |
| `endShareSession` | (cookie) | clears cookie |

Each public action: look up link by token hash (or share ID from the cookie), check status, expiry, lockout, max views and session version, then proceed.

## 12. Audit Logging

Add these action types. Entries never contain secret values, the token or the PIN.

| Action | Written when | Actor |
|---|---|---|
| `share.create` | Link created | Team member |
| `share.update_items` | Item selection changed | Team member |
| `share.extend` | Expiry extended | Team member |
| `share.regenerate_pin` | PIN regenerated | Team member |
| `share.revoke` | Link revoked | Team member |
| `share.unlock` | Lockout cleared manually | Team member |
| `share.delete` | Link deleted | Team member |
| `share.pin_success` | Client entered the correct PIN | Client (share ID, IP) |
| `share.pin_failed` | Wrong PIN | Client (share ID, IP) |
| `share.locked` | Lockout triggered | System |
| `share.reveal` | Client revealed or copied a secret | Client (share ID, item, IP) |
| `share.blocked` | Access attempt on expired, revoked or maxed-out link | Client (IP) |

Client entries have no `user_id`. Store the `share_link_id` as the actor reference and record the IP address and user agent. Entries appear in the project's audit log and in the link's access history.

## 15. Acceptance Criteria

The feature is done when:

1. A Manager can create a share link for a project, choose items, pick an expiry (30 days, 60 days, 120 days, 1 year or none) and receive a link and a 6-digit PIN once.
2. A client with the link and PIN can see only the chosen items and reveal or copy their secrets, without an account.
3. A client without the correct PIN, or with an expired, revoked or locked link, sees nothing.
4. A Manager can revoke, extend, regenerate the PIN and change the items at any time, and the change applies immediately.
5. Every client access and every team action appears in the audit log.
6. All 🔒 tests pass and the security review checklist is signed off by a teammate.
7. Documents are updated (`PRD.md`, `DECISIONS.md`, `ARCHITECTURE.md`, `SECURITY.md`, `TEST_PLAN.md`, `TASKS.md`, `MEMORY.md`).

## 16. Rules for Antigravity

- Read all project documents first. Work on one task at a time, starting with TASK-139.
- Do not skip the document updates in TASK-139. They record the exception to ADR-012.
- Do not change existing encryption, authentication or RLS code except where a task says so.
- Do not add new dependencies. Use Node's built-in `crypto` for token, PIN, scrypt and HMAC.
- Never store, log or return a plaintext PIN (after creation), a token (after creation) or a secret outside a reveal action.
- Do not weaken the limits in section 8 (attempt limits, lockout, generic errors, session re-checks, IDOR checks) to make a test pass or a feature easier.
- Use the existing `SecretField` and other shared components. Follow `DESIGN.md`.
- Use fake data only in tests and seeds.
- After each task: run lint, type check, tests and build. Update `MEMORY.md`. List files changed and anything uncertain.
- If something in this file conflicts with `RULES.md` or `SECURITY.md`, stop and ask instead of guessing.
