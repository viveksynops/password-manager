# Architecture

## Frontend
Next.js (App Router) + TypeScript + React

## UI Components
shadcn/ui (built on Base UI)

## Styling
Tailwind CSS

## Backend
Next.js server-side functionality (Server Actions and Route Handlers). There is no separate backend server.

## Database
Supabase PostgreSQL with Row Level Security (RLS) enabled on every table

## Authentication
Supabase Auth (email and password) + TOTP MFA, using `@supabase/ssr` for cookie-based sessions

## Encryption
AES-256-GCM, performed server-side only using Node's `crypto` module. The master key comes from a server-only environment variable.

## File Storage
Supabase Storage (private buckets), Phase 2

## Validation
Zod (shared by forms and server actions)

## Forms
React Hook Form + Zod resolver

## State Management
Zustand (for client-side global state if needed, e.g. cross-component UI state, search/filter states, modal controllers)

## Deployment
Vercel (or any host that supports Next.js), with a dedicated Supabase project for the vault

---

## High-Level Architecture

```
User
 ↓
Next.js UI (React Server Components + Client Components)
 ↓
Server Action / Route Handler
 ↓  ├── verify session + role
 ↓  ├── validate input (Zod)
 ↓  └── call service
Service Layer
 ↓  ├── encrypt / decrypt (lib/crypto)
 ↓  └── write audit log
Supabase Client (server)
 ↓
PostgreSQL (RLS enforced)
```

---

## Secret Flow

### Saving a secret
```
Form → Server Action → verify user + role → validate (Zod)
     → encrypt(value) → INSERT encrypted_value → write audit log
```

### Revealing or copying a secret
```
Click "Reveal" → Server Action → verify user + project access
               → fetch encrypted_value (RLS checked)
               → decrypt(value) → write audit log → return value to client
```

Secrets are never decrypted during page render. They are decrypted only when the user explicitly clicks Reveal or Copy.

## Layer Responsibilities

| Layer | Folder | Responsibility |
|---|---|---|
| **Pages** | `app/` | Routing, layout, fetching non-secret data |
| **UI** | `components/` | Reusable, generic UI with no business logic |
| **Features** | `features/` | Feature-specific components, forms and schemas |
| **Actions** | `actions/` | Entry point from UI: auth check, validation, call service |
| **Services** | `services/` | Business logic and all database operations |
| **Lib** | `lib/` | Infrastructure: Supabase clients, crypto, auth helpers |
| **Types** | `types/` | Shared TypeScript types |
| **Utils** | `utils/` | Small pure helper functions |

## Data Model Overview

```
users (Supabase Auth) ── profiles (role, status)
                             │
clients ── projects ── project_members (user ↔ project)
              │
              ├── credentials      (encrypted_password)
              └── env_variables    (encrypted_value, environment)

audit_logs (user_id, action, target_type, target_id, ip, created_at)
```

Structure: **Client → Project → Credentials + Env Variables**

## Access Control Model

| Role | Access |
|---|---|
| **Admin** | Everything, including team management and audit logs |
| **Manager** | Create and edit clients and projects, assign developers |
| **Developer** | Read credentials and env values of assigned projects only |

Access is enforced in two places:

1. **Server layer:** `requireRole()` check in every server action
2. **Database layer:** RLS policies, which are the final safety net

## Architectural Rules

### Separation of concerns
- UI components must not contain database logic.
- Database operations belong in `services/`.
- Business logic must stay separate from UI.
- Reusable UI belongs in `components/`. Feature-specific UI belongs in `features/`.
- Server actions only orchestrate (auth, validate, call service). They do not contain queries.

### Authentication and authorization
- Authentication must be verified server-side in every server action and route handler.
- Never trust the client for role or user identity.
- Every table must have RLS enabled, with policies written and tested.
- Middleware protects routes, but it is not the only line of defense.

### Secrets handling
- Passwords and env values are encrypted before they reach the database.
- Decryption happens only in server actions, only on explicit user request.
- Never decrypt in Server Components or pass secrets as page props.
- Never log secrets, decrypted values or the master key.
- `MASTER_KEY` and `SUPABASE_SERVICE_ROLE_KEY` never get a `NEXT_PUBLIC_` prefix and are never imported into client components.
- Mark crypto and service-role modules with `import "server-only"`.

### Audit logging
- Every view, copy, create, update and delete of a secret writes an audit log entry.
- Audit logs are append-only. No update or delete is allowed, even for admins.
- A failed audit write must fail the operation.

### Code quality
- All inputs are validated with Zod on the server.
- Use generated database types from Supabase. No `any`.
- Secret values in the UI are masked by default.
- Keep functions small and single-purpose.
- Handle errors explicitly and return safe, generic error messages to the client.

### Supabase usage
- Use the server client with the user's session for normal queries so RLS applies.
- Use the service role client only for admin-only tasks (inviting users) and never for reading secrets.
- All schema changes go through migration files in `supabase/migrations/`.

## Future Architecture (Phase 2)

```
Browser Extension (Vite + React + Tailwind)
 ↓
Next.js Route Handlers (/api/extension/*)
 ↓
Services → Supabase
```

- The extension authenticates with the same Supabase accounts and MFA.
- It never stores decrypted passwords. It requests one credential on demand.
- Domain matching and fill-on-click run in the extension. Decryption stays on the server.
